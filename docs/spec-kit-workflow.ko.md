# 개발 업무 워크플로

[English](spec-kit-workflow.md) · 한국어

Threadraft로 개발 환경을 준비한 후 Codex에서 요청을 검토하고, 이슈를 열어 작업을 이어 가거나 마치는 방법을 안내합니다. 아래 CSV 내보내기 사례의 요청과 작업 기록은 모두 예시입니다. 채팅에 입력할 문구는 [스킬 사용 예시](skill-usage.ko.md)에서 확인할 수 있습니다.

## 요청에 맞는 시작점

| 요청 | 시작 방법 | 다음 단계 |
| --- | --- | --- |
| 기존 CSV 버튼을 ‘CSV 다운로드’로 바꿔 달라는 요청처럼 바꿀 내용과 완료 기준이 분명함 | 진행 상황을 기록할 작업은 [`issue-create`](../.agents/skills/issue-create/SKILL.md)로 시작하거나 재개합니다. | 작업 문서에 바꿀 내용과 완료 기준을 적고 worktree에서 작업합니다. |
| 필터된 목록에 CSV 내보내기 기능을 추가하려는데 어느 행을 내보낼지 미정임 | `specify`로 기능이 어떻게 동작해야 하는지 적고, 그 동작을 정하는 데 필요한 질문은 `clarify`로 확인합니다. 구현 순서와 검증 방법은 `plan`에 기록합니다. | 작업을 순서대로 나눌 필요가 있을 때 `tasks`를 사용합니다. 설계 검토가 필요하면 EGM을 사용한 뒤 검토를 마친 문서의 링크를 이슈에 남깁니다. |
| 필터 결과가 0건일 때 내보내기 오류가 발생하지만 원인을 모름 | `bug` 확장이 설치된 경우 `bug.assess`로 증상과 정상 동작, 오류가 나는 조건, 원인으로 의심되는 부분과 그 근거를 정리합니다. | 조사만 요청받았다면 평가 문서를 전달하고 마칩니다. 수정 범위까지 승인받았다면 평가 문서를 이슈에 연결해 수정합니다. |
| 대량 내보내기를 백그라운드 작업으로 바꿀지 아직 결정하지 못함 | 아이디어 평가가 필요하고 `assess` 확장이 설치된 경우 진행할지와 그 이유를 정리합니다. | 진행하기로 했으면 기능 명세를 작성합니다. 더 조사하거나 중단하기로 했으면 이유와 아직 확인하지 못한 사항을 남깁니다. |

## 공통 흐름 · 이슈 시작부터 종료까지

| 단계 | 작업과 기록 |
| --- | --- |
| 이슈 준비 | `issue-create`에 이슈 키나 작업 문서 경로를 전달합니다. 같은 이슈가 있으면 기존 문서를 열고 해당 이슈의 worktree인지 확인한 뒤 이어서 사용합니다. 작업 문서는 worktree 밖에 두며, 프로젝트가 정한 문서 경로가 없으면 `docs/issues/<키>.md`를 사용합니다. 작업 범위, 완료 기준, 관련 문서 링크와 아직 확인할 사항을 기록합니다. |
| 기준 커밋과 worktree | 사용자가 승인한 기준 커밋에 worktree에서 사용할 파일이 들어 있는지 확인합니다. 새 저장소에 커밋이 없다면 사용자가 초기 커밋을 준비합니다. 기준 커밋이나 필요한 파일이 없으면 worktree를 만들기 전에 무엇이 빠졌는지 알립니다. 이슈 문서에는 worktree 경로, 브랜치, 기준 커밋을 남깁니다. |
| 구현과 인계 | 이슈 worktree에서 합의한 범위만큼 작업합니다. 연결된 `tasks.md`가 있으면 진행 상황을 업데이트합니다. 작업 문서에 완료 기준별 확인 결과와 근거를 볼 수 있는 곳, 아직 확인할 항목, 작업이 막힌 이유와 다음에 할 일을 적습니다. 다른 채팅에서 재개할 때는 이슈 키나 작업 문서 경로를 전달해 실제 Git 상태와 대조합니다. |
| 통합과 종료 | 프로젝트에서 정한 절차에 따라 변경을 반영하고 작업 문서에 커밋이나 PR을 링크합니다. 사용자가 완료 처리나 작업 중단을 승인하면 [`issue-close`](../.agents/skills/issue-close/SKILL.md)로 결과와 이유를 worktree 밖의 작업 문서에 기록합니다. 승인 대기 중에는 이슈를 열어 둡니다. 정리할 worktree와 브랜치가 해당 이슈의 것인지, 따로 보관해야 할 로컬 변경이 있는지 확인합니다. 브랜치의 마지막 커밋을 프로젝트가 승인한 브랜치나 태그 등의 Git ref에서 계속 찾을 수 있고 따로 보관할 로컬 변경이 없다면, 승인받은 범위에서 정리합니다. 정리가 막히면 이유와 남은 작업을 기록합니다. |

## 모의 사례 · 필터된 목록을 CSV로 내보내기

> 요청 — 목록의 필터 결과를 CSV로 내보낼 수 있게 해 주세요.

| 단계 | 가상 작업 흐름 | 다음 단계에 전달할 내용 |
| --- | --- | --- |
| `specify` | 필터가 적용된 목록을 CSV로 저장하는 동작과 완료 기준 초안을 적습니다. | `specs/csv-export/spec.md` |
| `clarify` | ‘현재 페이지’와 ‘필터 결과 전체’ 중 내보낼 범위를 확인합니다. 예시에서는 모든 페이지의 필터 결과를 내보내고, 결과가 0건이면 헤더만 저장하기로 합의합니다. | 합의한 동작을 반영한 `spec.md` |
| `plan` | 기존 필터 코드를 어떻게 재사용하고 CSV를 어떻게 만들지 적습니다. 결과가 여러 페이지에 걸쳐 있거나 한 건도 없을 때 무엇을 확인할지도 적습니다. | `specs/csv-export/plan.md` |
| `egm-review` → `egm-resolve` | 많은 행을 CSV로 저장하는 설계를 별도로 검토한다고 가정합니다. 리뷰에서 전체 결과를 한꺼번에 읽으면 메모리를 많이 쓸 수 있다는 지적이 나오면, 설계를 작성한 채팅에서 근거를 확인한 뒤 합의한 방법을 계획에 반영합니다. | 리뷰에서 확인한 문제와 합의한 해결책을 담은 `plan.md` |
| `tasks` | 구현을 나눠야 할 경우 필터 결과 읽기, 읽어 온 데이터로 CSV 만들기, 완료 기준 확인을 작업 순서대로 적습니다. | `specs/csv-export/tasks.md` |
| `issue-create` | 기준 커밋과 필요한 문서를 확인한 뒤 이슈를 시작합니다. `docs/issues/csv-export.md`에 문서 링크와 ‘모든 페이지에서 필터 조건에 맞는 행만 내보낸다’는 완료 기준을 적고 worktree를 연결합니다. | 이슈 키 `csv-export`, 작업 문서, worktree 위치와 기준 커밋 |
| `implement` → 필요 시 `converge` | `tasks.md`를 사용하는 경우 worktree에서 각 항목을 구현합니다. `converge`로 명세·계획·작업 목록을 구현과 대조해 결과가 0건일 때의 처리가 빠진 것을 발견했다고 가정합니다. 누락 항목을 `tasks.md`에 추가하고 `implement`로 처리합니다. | 업데이트한 작업 목록과 완료 기준별 확인 결과 |
| `issue-close` | 가상의 확인 결과인 ‘여러 페이지에서 필터에 맞는 행만 저장되고 0건일 때 헤더만 남는다’를 작업 문서에 적습니다. 변경이 반영됐고 사용자가 완료 처리를 승인했다고 가정합니다. 작업 문서에 PR과 완료 결과를 남기고 worktree를 정리할 조건이 갖춰졌는지 확인합니다. | 작업 문서의 종료 기록과 남은 정리 항목 |

## 모의 사례 · 결과가 0건이면 CSV 저장 실패

> 요청 — CSV 내보내기에서 필터 결과가 0건이면 오류가 납니다. 헤더만 담긴 파일이 저장돼야 합니다.

| 단계 | 가상 작업 흐름 |
| --- | --- |
| `bug.assess` | 오류를 재현하는 절차와 정상이라면 어떤 결과가 나와야 하는지를 `assessment.md`에 적습니다. 첫 행에서 열 이름을 가져오는 코드가 오류의 원인일 수 있다고 기록합니다. 코드에서 확인한 사실과 더 확인해야 할 부분을 구분해 적습니다. 조사만 요청받았다면 평가 문서를 전달하고 종료합니다. |
| `issue-create` → `bug.fix` | 수정도 승인됐다고 가정합니다. `issue-create`로 `csv-empty` 이슈와 worktree를 준비하고 승인된 평가 문서를 연결합니다. `bug.fix`는 `slug=csv-empty`를 그대로 써서 평가 문서를 찾고, 승인받은 범위에서 무엇을 고쳤는지 `fix.md`에 남깁니다. |
| 확인 → `issue-close` | 결과가 0건일 때 발생하던 오류를 다시 재현했다고 가정합니다. 헤더만 저장된 결과와 근거를 기록합니다. 프로젝트에서 정한 절차에 따라 변경을 반영하고, 사용자가 완료를 승인하면 이슈에 결과를 남깁니다. |

## 공개 저장소에 게시

공개할 명세와 예시에는 가상 데이터와 저장소 루트를 기준으로 한 상대 경로를 사용합니다. 커밋 전 diff와 첨부 자료에서 인증 정보, 개인정보, 내부 경로, 비공개 링크와 원본 로그가 있는지 살피고, 외부에 공개할 수 없는 자료는 빼고 올립니다.
