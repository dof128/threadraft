# Spec Kit과 Beads 사용 절차

[English](spec-kit-beads-workflow.md) · 한국어

요청을 접수한 뒤 변경을 검증하기까지의 절차입니다. Spec Kit에는 기대 동작, 구현 계획, 구현 항목을 기록합니다. Beads에는 작업 담당자, 의존성, 전체 상태를 기록합니다. Git은 변경 이력을 관리하며, worktree를 사용해 구현 작업 공간을 분리할 수 있습니다.

## 요청에 맞는 절차 선택

| 요청 | 시작 방법 | 산출물 |
| --- | --- | --- |
| 작업 범위와 인수 기준이 명확함 | 추적이 필요한 작업은 Beads Task를 생성하거나 기존 Task를 사용합니다. | 착수와 검증에 필요한 정보가 담긴 Task |
| 기능의 동작이나 설계를 구체화해야 함 | Spec Kit의 기능 명세 절차를 사용합니다. | 기능 명세, 구현 계획, 구현 체크리스트 |
| 기존 동작에 문제가 있고 원인이나 재현 조건이 불명확함 | Spec Kit의 선택 확장인 `bug`에서 평가 단계를 사용합니다. | 관찰 결과와 기대 동작, 재현 근거, 미확인 항목, 수정 범위 제안 |
| 계획을 세우기 전에 아이디어의 추진 여부를 결정해야 함 | Spec Kit의 선택 확장인 `assess`를 사용합니다. | 추진·추가 확인·중단 결정과 그 근거. 추진이 결정되면 기능 명세를 작성합니다. |

불확실한 부분을 해소하는 데 필요한 단계까지만 진행합니다. 평가 문서 자체가 최종 산출물이 될 수 있습니다. 명령 호출 형식은 설치된 에이전트 통합에 맞춥니다. [기능 명세](https://github.github.io/spec-kit/reference/agentic-sdd.html) · [버그 평가](https://github.github.io/spec-kit/guides/bugfix.html) · [아이디어 평가](https://github.github.io/spec-kit/reference/agentic-assessment.html)

## 작업 준비와 연결

1. 기능 개발에서는 `specify`로 기대 동작과 인수 기준을 작성합니다. 답에 따라 작업이 달라지는 항목은 `clarify`로 확인한 뒤 `plan`과 `tasks`를 실행합니다. 생성된 `spec.md`, `plan.md`, `tasks.md`를 함께 검토하고, 필요하면 `analyze`로 문서 간 일관성을 확인합니다. 이 명령은 Spec Kit 에이전트에서 호출합니다. [SDD 명령 레퍼런스](https://github.github.io/spec-kit/reference/agentic-sdd.html)
2. 검토한 문서는 저장소 기준의 고정된 상대 경로에 둡니다. 버그는 검토한 평가 문서를 연결하고 승인된 수정 범위, 재현 절차, 검증 기준을 기록합니다.
3. 같은 범위의 Beads Task를 조회합니다. 일치하는 작업이 있으면 전체 ID를 재사용합니다. 새로 등록할 때는 합의한 범위와 인수 기준, 남은 검증 항목을 기록합니다. Task에 검토한 문서 경로를 기록하고, `tasks.md`가 있으면 상단에 전체 Beads ID를 적습니다. 양쪽 참조가 올바른지 확인합니다. [Beads](https://github.com/gastownhall/beads)
4. 한 단위로 할당하고 인수할 수 있는 변경은 Beads Task 하나로 관리합니다. 구현 단계별 진행은 체크리스트에 기록합니다. 일정, 담당자 또는 인수 기준을 독립적으로 관리해야 하는 작업은 별도 Task로 만들고 의존성을 기록합니다.

예를 들어 CSV 내보내기 기능의 문서는 `specs/csv-export/spec.md`, `specs/csv-export/plan.md`, `specs/csv-export/tasks.md`에 둘 수 있습니다. 가상의 Task `demo-a1b`에 세 문서를 연결하고 “내보낸 CSV에는 필터 조건을 통과한 행만 포함된다”를 인수 기준으로 기록합니다. 체크리스트에는 내보낼 행 선택, CSV 직렬화, 회귀 테스트를 적을 수 있습니다.

## 구현, 검증, 종료

1. 프로젝트가 Git worktree를 사용하면 독립된 worktree에서 작업을 열거나 재개합니다. 수정 전에 전체 Beads ID, 브랜치, 현재 커밋, 문서 경로를 확인합니다. Threadraft에서는 `task-open`으로 Task와 worktree를 준비합니다.
2. 구현하면서 체크리스트를 갱신합니다. 작업 상태와 차단 사유는 Beads에 기록합니다. 작업 범위나 인수 기준이 바뀌면 기준 문서와 Beads 기록을 함께 갱신합니다.
3. 인수 기준에 따라 결과를 검증합니다. 확인한 항목, 근거의 위치, 남은 검증 항목을 기록합니다. 인계할 때는 Task ID, 브랜치, 전체 커밋 SHA, 로컬 변경, 차단 사유, 다음 조치를 남깁니다. Threadraft에서는 `task-integrate`로 프로젝트 정책에 따른 검토, 인계, 재개, 통합을 진행합니다.
4. 프로젝트의 인수 및 통합 조건을 충족하면 Beads Task를 닫습니다. 결과를 기록하고 관련 커밋이나 Pull Request를 연결합니다. 작업을 폐기할 때도 결과와 사유를 기록합니다. Threadraft에서는 `task-close`를 사용하며, 필요한 변경과 근거를 보존한 뒤 worktree를 정리합니다.

## 공개 저장소에 게시

기여자가 활용할 수 있도록 검토한 명세, 인수 기준, 검증 요약을 공개합니다. 예시는 가상 데이터로 작성하고 경로는 저장소 기준 상대 경로를 사용합니다. 커밋 전에 diff와 첨부 자료에 인증 정보, 개인정보, 비공개 이슈 링크, 내부 경로, 원본 로그가 포함됐는지 확인합니다. 비공개 근거, 로컬 Beads 데이터베이스, 에이전트의 임시 출력은 공개 커밋에서 제외합니다. 프로젝트에서 Beads 데이터를 공유하는 경우 내보낸 Task 기록과 첨부 자료도 소스 파일과 같은 기준으로 검토합니다.
